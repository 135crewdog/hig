Start here

These guidelines are for small Progressive Web Apps: plain HTML, CSS and JavaScript, hosted on GitHub Pages, opened mostly on an iPhone. Show Time and Apollo are the working examples.

Bottom line: use the operating system's and the browser's defaults. They are the simplest choice and the one most likely to keep working.

Apple's Human Interface Guidelines are the base. This page lists only what a web app changes or adds, and does not repeat Apple.

A new project starts by copying the starter, a blank app that already follows every rule here. Its CLAUDE.md says: Follows the HIG at https://135crewdog.github.io/hig/.

More

Which rule wins: the project's own CLAUDE.md, then this page, then Apple's. A project that departs from this page says so in its CLAUDE.md, with the reason.

Units: read Apple's "pt" as CSS px. They are the same in Safari at the default zoom.

Changing a rule is a pull request to the repository with the reason. A rule that came from a bug names the bug under Lessons learned. This page is the HIG; there is no other copy.

Principles

  1. Use the defaults. Native controls, the system font, the device's theme, time zone, date format, zoom and scrolling. Change a default only when the use case needs it, and write down why.
  2. Simple. Do one job, with the fewest files, settings, screens and words that do it. When in doubt, leave it out.
  3. Future-proof. Only standard web features: no framework, no build step, no runtime dependencies. Code written today runs unchanged in ten years. The user's data lives somewhere the user owns, never only inside the app.
  4. Offline first. The app opens and works with no connection, and nothing typed is lost to a bad signal.
More

Defaults come first because they are the work someone else maintains. The browser's date picker, zoom, scrolling and dark mode get better every year at no cost; a custom version only gets older. Apple says it too: include just what's necessary; simplicity isn't minimalism.

Apple's eight principles, in one line each:

  • Purpose: make something meaningful.
  • Agency: stay out of the way; every action can be undone or is confirmed.
  • Responsibility: collect only what is needed.
  • Familiarity: known patterns, used the same way everywhere.
  • Flexibility: accessible from the start.
  • Simplicity: see above.
  • Craft: test on a real phone; shipping isn't the finish line.
  • Delight: make it human.

Broad or focused

Every app says in its CLAUDE.md which way it leans. The question is who it is designed for:

  • Broad: many people, or many kinds of device. Apollo leans broad.
  • Focused: a small group who all use the same kind of device. The app names it, for example "iPhone, installed to the Home Screen". Show Time leans focused.

Both use the defaults. Scope only decides whose defaults: everyone's, or those of the one kind of device.

The same for both: Light, Dark and Auto themes; 44px tap targets; readable contrast; the device's clock unless the use case needs another; offline first; tests.

More

Scope is a lean, not a box. An app may take one rule from the other side; it writes down which, and why. The starter is broad, because loosening a rule is easier than adding one back.

Show Time's sliding tabs, 430px width and disabled zoom are focused choices for a phone in a cockpit. Apollo's instant tabs, 720px column and default zoom are broad choices for whatever device a crew member has.

Foundations

Color

Colors are CSS variables on :root, with dark values that override them. The grays, blue and red are Apple's iOS system colors; see More for the exceptions. The starter's style.css holds the full list.

  • One accent per app. It defaults to iOS blue; an app may set its own. Use it on primary actions and the selected state, not as decoration.
  • Never one color for two meanings, and never color alone: pair it with a word, as in an OVERDUE badge.
More

Secondary text is #656569 in light mode, not Apple's #8e8e93, and error text is #b3261e. Apple's gray fails the 4.5:1 minimum for regular text on white; Apollo darkened both after an audit, because readability wins over matching.

The accent and destructive colors are #007aff and #ff3b30, iOS blue and red as Apple published them until 2025 and as both apps use them. Apple now lists #0088ff and #ff383c and says its documented values change between releases, so these stay on purpose. They are used only on bold labels and buttons, where 3:1 applies (white on #007aff is 4.0:1, #ff3b30 on white about 3.5:1). Regular-weight text never uses them, and regular text on --fill uses --text, because --text2 on --fill is only 3.2:1 in dark.

Apollo's accent is red #e06666 with dark text, drawn from its due-date colors. Banners use their own warning and error tokens (amber for caution, red for warning, the aviation convention). Apple publishes no values for its label and separator colors, so these come from Show Time and Apollo.

Theme

Every app has Light, Dark and Auto in Settings. Auto is the default and follows the device's setting, including a change while the app is open.

More

Apple advises against an in-app appearance setting. It stays on purpose: someone may want dark in a cockpit while the phone stays light.

How: a data-theme attribute on <html> picks Light or Dark, and Auto is plain CSS: the dark values sit under :root[data-theme="dark"] and again under @media (prefers-color-scheme: dark) for :root:not([data-theme="light"]). The repetition is the price of the first paint matching the device before any script runs. color-scheme is set with the values, so native controls match too. Stored values are light, dark, auto.

The status bar is the browser's. After each change <meta name="theme-color"> takes the header's color for the browsers that read it (Chrome, Android). Safari on iPhone ignores it and colors its bars from the page background, so there the status bar is --bg. That is the default and it is accepted: forcing it would take a background on html sized to the screen, which the layout rules forbid.

No system setting? Every current browser reports one. If an app ever targets one that doesn't, consider having Auto follow sunrise and sunset instead.

Type

The system font, at Apple's iOS text sizes. Nothing anyone must read is smaller than 13px.

More

The stack is -apple-system, BlinkMacSystemFont, "SF Pro Display", "Helvetica Neue", sans-serif, with -webkit-font-smoothing: antialiased. It gives SF Pro on Apple devices without embedding it, which Apple's license forbids. The system font adjusts its own letter spacing, so body text gets none; the 34px title takes -0.5px.

Set text-size-adjust: 100% on html, or Safari enlarges some text in landscape and not the rest. Numbers that line up use font-variant-numeric: tabular-nums. Weights are 400, 600 and 700; never light or thin.

Layout

  • The app is an ordinary web page. The browser owns the viewport, scrolling, the status bar, the keyboard and zoom. Nothing is sized to the screen height or the safe area.
  • One centered column: 720px for broad apps, the device's width for focused ones. No breakpoints.
  • The only thing that sticks is a save bar, with position: sticky. The header scrolls away with the page.
More

Never use vh, dvh, height: 100% chains, position: fixed; inset: 0 or env(safe-area-inset-*). The page background is the app's background, so nothing can show behind it. Apollo learned this the hard way (see Lessons learned).

Spacing is on an 8px grid: header 16px by 20px, panel 20px, 24px between sections, 8px from a section title to its card, 16px inside a card and between fields, 12px between buttons. Radii: 10px for cards, inputs and banners; 12px for full-width buttons; 9px and 7px for the segmented control. Borders are 1px. Shadows only on the selected segment and the toast.

Accessibility

  • Every tap target is at least 44 by 44px. A control may look smaller; its tap area may not be.
  • Text contrast follows Apple's table in both themes: 4.5:1 for regular text up to 17px, 3:1 for text 18px and up or bold. Apple doesn't say which weight is bold; this page counts 600 and heavier.
  • Zoom: broad apps leave it to the browser. A focused app may disable it when that serves the use case.
  • Motion stops when the device asks for reduced motion.
More

The broad viewport line is exactly <meta name="viewport" content="width=device-width, initial-scale=1">. A focused app that disables zoom adds maximum-scale=1, user-scalable=no and says why in its CLAUDE.md.

Visible keyboard focus: :focus-visible { outline: 2px solid var(--accent) }. Reduced motion: transitions off under @media (prefers-reduced-motion: reduce). Use HTML for what it can do (<button>, <label for>, <h1>), then ARIA for the rest: tabs with role="tab", aria-selected and arrow keys; aria-pressed on toggles; aria-label on icon buttons; role="status" on toasts and role="alert" on banners; aria-describedby from a field to its error. A gesture always has a visible control that does the same.

Time and dates

  • The device's clock and time zone, unless the use case needs another. Apollo runs on Zulu because aviation does.
  • Dates a person reads are in the device's own format (Oct 7, 2026 in the US). The native date picker shows them that way already.
  • Dates a machine reads are YYYY-MM-DD, everywhere.
More

Format with toLocaleDateString(undefined, { dateStyle: 'medium', timeZone: 'UTC' }) on a new Date(0) set with setUTCFullYear(y, m - 1, d), so no time zone moves it a day (not Date.UTC, which reads a year below 100 as 19xx). An app whose users share a convention may use it instead and say so: Apollo shows 07-Oct-26 and runs every date on Zulu, where "today" is new Date().toISOString().slice(0, 10).

Writing

  • Sentence case everywhere. Section titles are written that way and uppercased by CSS.
  • Buttons start with a verb: "Save 2 rows", "Sync now". Tab labels are nouns, as Apple asks: "Entry", "Status".
  • Errors say what to do: "Enter the mission number." Not "Invalid mission number."
  • Short. If a sentence can lose a word, it does.
More

Proper nouns keep their capitals (Zulu, Task ID). A status flag may be capitals on purpose (OVERDUE). "Cancel" is always "Cancel"; never "Yes" and "No"; no "OK" where a verb fits (the browser's confirm() is the exception; see Components). Errors end with a period and give the next step: "No connection. Rows are saved on this device and will sync later." No "oops", no blame, no "we". Count correctly: "1 row", "2 rows". Use "tap" only in an app made for phones; otherwise "choose".

Icons

The app icon is a simple shape or one word on a solid or gradient square. In the app, icons are emoji or small inline SVGs.

More

One SVG is the source; render-icons.js in the starter makes the 192 and 512px PNGs from it. The square is full-bleed and opaque, because iOS rounds the corners. No icon fonts, no icon library, and no SF Symbols artwork (its license). Follow Apple's metaphors: ⚙ settings, + add, − remove, × close, ✓ done.

Components

Every one is styled in the starter's style.css; its screens show all but the toggle group, stepper, secondary button and badge, which wait there for the first app that needs them. Native first: the browser's own date picker, select menu, search field and confirm dialog come before anything custom.

More

Header: --elev with a bottom border; the gear is ⚙ on --fill with aria-label="Settings". Settings: Done is 17px, 600 weight, in the accent, on the trailing side as Apple places it; a spacer balances the left.

Segmented control: track --fill, 13px labels in --text, the selected one --elev and 600 weight with a small shadow. It scrolls the page to the top. The swipe counts only when horizontal movement dominates (vertical at most 0.75 of horizontal) and passes 50px. A touch that starts in a field is never a swipe, so moving a cursor can't change the screen. Broad apps switch instantly; focused apps may slide.

Input: 17px because Safari zooms the page into any field under 16px. Set inputmode, autocomplete, autocapitalize and spellcheck to suit the field; mark an error with aria-invalid and a red border. Buttons, text fields, the date field and selects drop the native look (appearance: none) so every control shares the app's shapes; the pickers, menus and keyboards they open stay native, and only checkboxes keep the browser's drawing. On iPhone a natively drawn date field is sized by Safari, which widens it past width: 100%, and its value is centered, so ::-webkit-date-and-time-value { text-align: start } lines it up. Select: the input's fill, border and 10px corners, a chevron (a background image per theme) so it still reads as a menu, and height: 44px rather than min-height, which Safari on iPhone replaces with its own 30px when it draws the select.

Button: padding 16px, 17px 600 weight, disabled at half opacity. A slow action changes its label ("Syncing…") and is disabled until done. At most one or two accent buttons on a screen. Stepper: the count is 17px bold with tabular numbers, regular weight at zero, with labels "Add one ⟨name⟩" and "Remove one ⟨name⟩".

Toast: fixed at the bottom center, inverted colors, role="status". It stays in the page and is emptied, never hidden with display: none, so screen readers announce each message. Never for an error that needs action: that goes in a banner or beside the field. Settings: every setting applies the moment it changes, so there is nothing to cancel, and Done alone closes the screen; Apple pairs Done with Cancel on a sheet. Opening Settings moves focus to Done, and Done returns it to the gear. Confirm: its buttons are the browser's Cancel and OK, the one place OK stands where Apple would put a verb, because a native dialog beats a custom one. So the text is a question OK plainly answers, saying what will and won't be touched. alert() is never used.

Patterns

  • Screens: one main view with up to four tabs, and Settings. No other navigation, no modals.
  • First run: if the app can't work until something is set, it opens on Settings until it is. No tutorial.
  • Feedback matches the moment: a field error beside the field, a screen problem in a banner, success in a toast, destroying data in a confirm.
  • Saving offline: a save lands on the device at once and syncs when it can. A retry never doubles it.
  • Defaults are filled in: today's date, the last choice. An untouched date moves on to the new day.
More

Settings order: what the app needs (Connection), Appearance, Data (Clear local data, which confirms), Help (Guide, Send feedback), then the version line. Settings holds rarely changed options; a filter or a mode belongs on its own screen.

The offline queue: each save is a batch with a fresh crypto.randomUUID() id, stored before any network call. Sync sends batches in order and removes each only when the server acknowledges its id; the server ignores an id it has seen. Sync runs on load, after a save, on online, on visibilitychange when there is work, and from Sync now.

Storage can fail. save() returns true or false, and on false the user's input stays on screen with a message. Never report "saved" for something that wasn't, a setting included. Stored values are checked on load: anything an older version or a damaged store left is normalized to the shape the app expects, so the app always opens. Read before writing: a list kept in one key is read from storage, not memory, just before it is written, so an entry another tab saved is kept.

Late replies are dropped: Clear or a connection change bumps a counter, and a reply from before it is ignored. One editing tab: where two tabs could write the same queue, a heartbeat lock in localStorage lets one edit and the others read; storage events keep them in step.

Connecting a device: a link carries the address and token in the fragment (#url=…&token=…), which browsers never send to the server. The app saves it and removes it from the address bar. Apps Script: POST with Content-Type: text/plain, which needs no CORS preflight.

Engineering

  • HTML, CSS and JavaScript only. No framework, no build step, no runtime dependencies, no scripts from a CDN.
  • Pure functions are tested in Node, and the page is driven by a browser test in CI. The site deploys only after both pass.
  • The service worker fetches from the network first and falls back to its cache offline. It deletes only its own old caches.
  • Every change to the app bumps its version in both places, or devices keep the old copy.

app.js has pure helpers at the top with no DOM, the page code inside if (typeof document !== 'undefined'), and module.exports at the bottom, so the tests import the code the app runs. Never copy logic into a test. If a backend computes something, the app displays it and doesn't compute it again. Plain var/function JavaScript, 'use strict', comments that say why.

The head: charset, viewport, theme-color, apple-mobile-web-app-title, the manifest, an SVG icon and the 192px PNG as apple-touch-icon. Nothing else: no apple-mobile-web-app-capable, no status-bar style. The manifest: start_url and scope both ./ (relative, for a GitHub Pages subpath), display: standalone, no orientation lock, background_color matching --bg, PNGs marked any maskable.

The service worker: network first for every same-origin GET, with fetch(req, { cache: 'no-cache' }), storing each good reply; the install precaches with the same no-cache requests, so it never saves a copy left from before the deploy. Other origins and other methods pass through untouched. Offline, the app's own address falls back to the cached app; any other page says it's offline. Caches are named <app>/<version>, and activation deletes only caches that start with <app>/, because every app on 135crewdog.github.io shares one cache storage. The slash can't appear in an app name, so starter/ never matches another app's starter-kit/. The precache list matches the shipped files exactly, because one missing file fails the whole install.

Versions are dates: YYYY.MM.DD.N, in APP_VERSION in app.js and VERSION in sw.js. A unit test fails if they differ. Storage: localStorage, with keys prefixed by the app's name: <app>.settings, then one key per kind of data, named for what it holds (the starter's starter.entries; Apollo's apollo.data, apollo.queue, apollo.lock); every read has a fallback, every write reports success. It is plain text, so tokens stay low-value and are never committed.

Tests: spec tables are copied into tests word for word, and an expected value is never changed to make a test pass. Tests never depend on today's date; they fix the clock or derive the answer from the rules. The browser test runs at 390 by 844, fails on any page error, checks every tap target on every screen, and saves screenshots when given a folder. It runs in Chromium, which draws native controls its own way, so it can't see how Safari on iPhone sizes a select or a date field, colors the status bar or shows the date picker: those are checked on the phone. Playwright is installed in CI with --no-save and never committed.

Process

  • CLAUDE.md is the spec. Code that disagrees with it is wrong.
  • Propose before building. Agree the solution, then build it.
  • A pull request waits for review. It is never merged unasked.
  • A pull request says what it was checked on. Native controls, the status bar and the date picker can only be judged on the device, so the devices in the "Checked on" row are opened before merging.
  • Ask before adding anything not in the spec. Ideas not adopted go under "Parked".
More

The Parked list keeps a discussed idea from being proposed again or built by accident. An audit goes into a file with a severity for each finding and the decision made on it.
